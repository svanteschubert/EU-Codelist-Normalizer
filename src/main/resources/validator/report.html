1. Validator against the code lists, per effective date

Each code-list rule of the validator (BR-CL-01 to BR-CL-26) checks an invoice field against a list of codes written into the rule. Every such list is compared, code by code, with the code list the Commission published for the same date, once as Genericode and once as spreadsheet.

How to read a cell, for example 7 of 22 rules · 11 codes differ:

  • 22 rules of this syntax could be compared with this component. The Genericode column can count one fewer: BR-CL-06 checks the Time sheet, which was never published as Genericode.
  • 7 of them implement a different set of codes than the component lists.
  • 11 codes differ across those 7 rules, counted once per rule. A code both BR-CL-03 and BR-CL-04 get wrong counts twice, because both checks fail an invoice.
  • all 22 agree: every rule implements exactly the listed codes. not published: that release has no such component; before 2021 the code lists were published as spreadsheet only.

Hover over a cell for the rules concerned; click it for their codes.

2. Index sheet against the code lists: claimed and actual changes

The first sheet of every “EN16931 code list values” workbook, Index, states per tab whether the list changed since the previous release (column “Changes”) and how (column “Remark on updates”). Here each claim is set against what actually changed: in the tab's own spreadsheet sheet, compared with the release before, and in the Genericode file, compared with the last release that had one. A row disagrees when the Index names a change that did not happen, misses one that did, or names a code the list does not contain. Every release revision is checked, including corrected ones. Rows that disagree come first; the complete table is in index-claims.csv.

5. Validator: codes that differ, per effective date

Per effective date, grouped by syntax and by the component compared with. Each differing code is on a line of its own, in code order, with its name from the published code list: implemented, not published means the validator lets an invoice use a code the published list does not contain; published, not implemented means an invoice using a published code fails validation. For a code the compared release does not list, the name comes from the nearest release that did. Hover over a line for its source. The complete lists, including rules that agree, are in rules.csv.

6. Files in this report

All CSV files are UTF-8, with every field quoted. Codes within a field are separated by spaces, in the order the normalized code lists use. Every file is listed with its size and SHA-256 in manifest.json, so a copy of this folder can be checked for completeness.

Validator codes are read from the tagged releases of the eInvoicing-EN16931 repository; effective dates come from validator-releases.csv, and the rule-to-code-list mapping from rule-catalog.csv. Where a rule states several lists — UBL's BR-CL-01 for invoices and credit notes, UBL's BR-CL-10 with the additional SEPA scheme — their union is compared.
